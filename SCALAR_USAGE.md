# Using Scalar UI to test the DamiFYP API

This guide shows how to use the Scalar UI that is embedded in the project to exercise the API endpoints we recently added: request-scoped `UserProfile`, business-role policy-based authorization, and the middleware that injects the profile per request.

Quick summary
- Start the API locally
- Open Scalar UI (Swagger-like UI) at `/scalar`
- Authenticate (OAuth2 or manual login) so Scalar will send a bearer token
- Call endpoints and observe responses (401 / 403 / 200)

Prerequisites
- .NET SDK installed
- The project configured to run locally (see `Config/Development/appsettings.Development.json` for Keycloak / OAuth2 settings)
- A running database with at least one `User` record you can log in with (or create one)

1) Start the API

Open a terminal in the repository root and run:

```powershell
Set-Location "C:\Users\User\RiderProjects\DamiFYP"
# run the web project (adjust to the correct profile if needed)
dotnet run --project .\DamiFYP\DamiFYP.csproj
```

By default the project exposes both HTTP and HTTPS URLs. The `launchSettings.json` includes `https://localhost:7212` and `http://localhost:5023` in the dev profile. The Scalar UI is mounted at `/scalar`.

2) Open Scalar UI in your browser

- HTTPS (if you use the HTTPS launch profile): https://localhost:7212/scalar
- HTTP (alternate): http://localhost:5023/scalar

You should see a generated UI listing all endpoints in the API.

3) Authentication options in Scalar

There are two ways to get a bearer token into Scalar so requests are authenticated:

A) Use OAuth2 (Authorization Code) in the Scalar UI
- Click the "Authorize" button in the top-right of Scalar.
- If OAuth2 is configured correctly (see `Config/Development/appsettings.Development.json`) you will see an OAuth2 flow (Authorization Code) you can use.
- This will redirect to Keycloak (or your configured IdP) to sign in and Scalar will receive an access token which it will attach to subsequent requests.

B) Manual token (useful for local testing)
- Use the local login endpoint to get a token quickly:
  - POST `/api/Login` with JSON body (replace with a real user from your DB):

```json
{
  "userId": 123,
  "userName": "Test User",
  "email": "test@example.com"
}
```

- The endpoint returns a JSON object with a `token` string. Copy that token.
- In Scalar click "Authorize" and paste the token into the `Bearer` field (or use the `Bearer` auth option). After authorizing, Scalar will attach the Authorization header to your requests.

Notes about token format
- Tokens generated by the local login currently include a `sub` claim containing the `userId` (this is what the middleware uses to resolve the profile).
- Roles in the token are string values (the app uses `user.Role.ToString()` when issuing tokens from the local login). If you rely on Keycloak for auth, ensure Keycloak role names match the values your policy expects (see mapping notes below).

4) What to test (endpoints & expected behavior)

A. Test unauthenticated access
- Try: GET `/api/conversation/get-all-conversations`
- Expected: 401 Unauthorized (no token provided)

B. Test policy-based access (business role)
- Login as a user who has business role `Donor` or `ManageAccount`.
  - If you create a test user directly in the DB, assign the `Role` column the integer value that maps to `BusinessRole.Donor` (see enum below).
- With a valid token provided in Scalar, call:
  - GET `/api/conversation/get-all-conversations`
- Expected: 200 OK (if user is Donor/ManageAccount)
- If token lacks the business role: 403 Forbidden

C. Test creating a donation request
- You can inspect available blood types first: GET `/api/BloodType/GetAllBloodTypes`
- Create a donation request (sample body) — adjust fields as needed:

```json
{
  "userId": 123,
  "bloodTypeName": "Aplus",
  "quantity": 2,
  "latitude": 1.234,
  "longitude": 2.345,
  "urgencyLevel": "High",
  "neededByDate": "2026-07-10T00:00:00Z"
}
```

- POST `/api/DonationRequest` with the body above.
- Note: currently the controller still accepts `userId` from the client. Best practice is to have the server set `UserId` from the injected `UserProfile` (the middleware + profile service are available for that change).

D. Expected status codes
- 401 Unauthorized: no token or invalid token
- 403 Forbidden: token valid, but business role policy denied
- 200 / 201 OK / Created: token valid and policy passed

5) Decode tokens / inspect claims
- If you want to inspect what claims are present in the token, copy the token and paste it to https://jwt.io/ (or any JWT decoder). Look for these claims:
  - `sub` — should match the numeric user id stored in your DB
  - `role` / role claims — roles used for RBAC and admin bypass

6) Database notes & enum mapping
- `BusinessRole` enum is defined in `DamiFYP.Domain.Models.BusinessRole` with values:
  - `None = 0`
  - `Admin = 1`
  - `Donor = 2`
  - `Seeker = 3`
  - `ManageAccount = 4`

- The `User.Role` property in the domain is now of type `BusinessRole`. By default EF Core will map that to an integer column in the database.

- If you need to seed or insert a user directly into the DB, set the `Role` column to the above integer values. Example SQL (Postgres):

```sql
INSERT INTO "User" ("Name","Email","PasswordHash","Role","IsAvailable")
VALUES ('Test Donor','donor@example.com','<hash>', 2, false);
```

Adjust other required fields as needed.

7) Troubleshooting
- If Scalar's OAuth2 flow doesn't show an "Authorize" button or you cannot sign in with Keycloak, fall back to the manual login flow (`/api/Login`) and paste the returned token.
- If you receive 403 but expect 200: verify the DB `User.Role` value and the token's `sub` claim match the record you used for Login.
- If the token's role string doesn't match the role names used by your policies, consider adding a mapping layer between enum values and token role strings. I can add an explicit mapping if you want tokens to carry different role names (e.g. lowercase/hyphenated role names used by Keycloak).
